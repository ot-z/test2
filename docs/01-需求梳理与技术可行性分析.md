## 1. 结论摘要

**整体结论：项目可行，建议立项；但原方案中有一条需求必须做范围收窄，另有一个安全问题必须立即处理。**

- **可落地**：本地单机 Web 应用（浏览器访问 `127.0.0.1`）+ SQLite 单文件数据库，单人使用、无需账号、无需云部署，日常离线可用。
- **必须收窄**：「自动搜索各大刷题网站的题目并按知识点分类」不能实现为通用全自动爬虫。受 `robots.txt`、版权和反爬限制，应改为 **「公开 API 同步题目元信息 + 站内标签归一 + 外链跳转 + 人工/AI 辅助标注」**。题面、样例、官方题解不批量落库。用户随后在 `题目爬虫方案修正.txt` 中提出「浏览器内 AI 总结」与「直接爬虫」两种候选，评估与推荐组合见**第 9 节**。
- **必须立即处理**：原始方案中以明文写有 DeepSeek API Key。该密钥已出现在本地文件与对话上下文中，应视为已泄漏，**请立即到 platform.deepseek.com 撤销并重建**。本项目所有文档、代码、git 历史中均不得出现真实密钥。
- **建议节奏**：先做不依赖爬虫、不依赖大模型的「每日刷题闭环」MVP，再逐步接入数据源与 AI。避免一上来同时踩爬虫、模型、前端三个坑。

## 4. 技术可行性逐项分析

### F1 题库自动采集 —— 全局最大风险点，需降范围

各目标站点的实际可行性（依据见附录「核实来源」）：

| 站点 | 数据获取方式 | 是否官方 | 合规情况 | 稳定性 | 本项目建议 |
| --- | --- | --- | --- | --- | --- |
| Codeforces | 官方公开 REST API，`problemset.problems` 一次返回全量题目及 `tags`、`rating`、`solvedCount`，免登录 | ✅ 官方 | 良好 | 高（JSON 契约，不随前端改版失效） | **自动全量同步元信息，首选数据源** |
| AtCoder | AtCoder Problems（kenkoooo）公开 JSON：`problems.json`、`merged-problems.json`、`problem-models.json`（含难度估计） | ❌ 第三方 | 可用，要求访问间隔 > 1 秒 | 中（作者会废弃旧 API） | 可选适配器，缓存 + 限速 + 失败降级 |
| 洛谷 | 无官方公开 API；第三方只读工具可取元信息，列表页抓取依赖登录 Cookie、有反爬 | ❌ | 灰色 | 低 | **不做自动抓取**，手工/批量粘贴导入题号，仅存外链 |
| LeetCode | 无官方批量 API；`robots.txt` 明确 Disallow `/api/`、`/graphql`、`/submissions` 等；Cloudflare 反爬；题面与题解受版权保护 | ❌ | **不合规** | 低 | **不抓取**；仅手工录入题号与外链 |
| 蓝桥杯官网题库 | 无公开 API | ❌ | 灰色 | 低 | 手工录入；大纲作为本地配置维护 |

**结论**：把「自动搜索各大刷题网站」重新定义为 **「分级数据源适配器 + 本地题目元信息目录」**。这一改动不损失你的实际使用价值——你要的是「不用手动找题、点链接就能跳过去」，而这些完全可以由元信息目录 + 外链满足。同时规避了封禁、改版和版权三类长期风险。

> 这条是本次分析中**唯一需要你明确同意的范围调整**，见 D-02 / D-03。

### F2 分类体系（知识点 / 数据结构 / 算法 / 难度）

- **难点**：各站标签不可直接对齐。Codeforces 用英文标签（`dp`、`graphs`、`greedy`），洛谷用中文算法标签；难度量纲完全不同（CF rating 800–3500、洛谷 0–7、蓝桥杯大纲 1–10）。
- **方案**：
  1. 自建 `knowledge_nodes` 知识点树，三个维度用 `category` 区分（知识点 / 数据结构 / 算法），支持父子层级。
  2. `tag_mappings` 映射表把外部标签归一到内部节点，映射可人工维护、可版本化。
  3. 难度统一为 5 档（入门 / 基础 / 进阶 / 提高 / 竞赛），各来源配置分段映射规则，允许人工校准。
  4. 无标签题目用 DeepSeek 的 JSON 模式输出候选标签（`response_format: {"type":"json_object"}` + prompt 中显式要求 JSON），**标记为 AI 建议，人工确认后才写入**。调用成本极低。
- **可行性**：🟢 高。但「完全自动且准确」做不到，需保留人工确认环节。

### F3 按比赛大纲自动组题

- 蓝桥杯官方发布过《软件赛知识点大纲》PDF，含组别、知识点清单与 1–10 难度系数（如大学 B 组覆盖枚举、排序、搜索、贪心、模拟、二分、DP、字符串、图论、数学、数据结构等）。
- **但**：大纲逐年更新、PDF 非机器可读、无接口 → 不能「自动爬取大纲」。
- **方案**：把大纲做成仓库内 `config/syllabus/*.yaml` 的**版本化配置**，内置一份基线（含来源 URL 与生效日期），支持在界面里编辑/导入。组题算法：大纲知识点 → 映射标签 → 过滤难度区间与未学题目 → 按优先级/通过率排序 → 生成**候选题单** → 预览、剔除、调整顺序 → 确认后写入计划。
- **可行性**：🟡 中高。「自动」= 自动生成候选题单，不是黑盒全自动；这一步的人工确认是有价值的，因为它决定你未来几个月的刷题顺序。

### F4 复习调度（原方案核心机制）

- 你描述的是**固定节奏**：`new_per_day = 1`，第 8 天起每天再加 `review_per_day = 1`，复习对象为约 7 天前学过的题。实现上只需一张 `daily_plan_items` 表 + `due_date` 字段，复杂度低，🟢 完全可行。
- **需要指出的三点**：
  1. **语义歧义**：「再刷一道之前学习过的题目」按字面是「每天固定 1 道旧题」，不是「把历史所有题都复习一遍」。若为后者，第 N 天任务量会线性膨胀到不可执行。按字面实现，见 D-05/D-06。
  2. **机制局限**：所有题目统一 7 天间隔、只复习一次、不区分掌握程度。对「一眼会」和「卡了两小时」的题同等对待，复习效率会随时间下降。
  3. **改进路径**：MVP 严格按你的规则实现且参数可配；M4 引入 SM-2 简化版（每次复习打分 1–5，动态调整下次间隔）。数据结构在 M1 就预留 `ease_factor`、`interval_days`、`repetition` 字段，届时无需改表。
- **必须明确的边界**：漏打卡顺延、手动跳过、暂停区间、题目完成后是否退出复习池（见 D-07/D-08）。

### F5 进度管理与历史记录

- **设计要点**：`daily_plans` 是**每日任务快照**，生成后不再随题目库变动而改变；`study_records` 记录实际结果。这样三个月后回看，历史不会被后续编辑污染。
- 笔记用 Markdown 存储，支持代码围栏高亮与自动保存（防抖）。
- 可提供三种视图：日历/按日、按题、按知识点；以及基础统计（连续打卡、累计题量、知识点覆盖热力图）。
- **可行性**：🟢 高，纯 CRUD + 聚合查询，SQLite 足够（万级题目、千级记录下毫秒级响应）。

### F6 大模型智能体（DeepSeek）

**核实到的当前事实（2026-11）**：

| 项 | 值 |
| --- | --- |
| API 格式 | OpenAI / Anthropic 兼容；OpenAI 模式 `base_url = https://api.deepseek.com`（无 `/v1` 后缀） |
| 当前主推模型 | `deepseek-flash`（DeepSeek-V4.1-Flash-1017，最便宜，支持图片/工具/Agent）、`deepseek-v4-pro`（强推理）、`deepseek-v4-flash-vision-exp`（实验视觉） |
| 已停用 | `deepseek-chat`、`deepseek-reasoner` 已于 **2026-07-24** 下线；`deepseek-v4-flash` 为旧名，路由到 V4.1-Flash |
| 关键参数 | `stream`、`thinking: {"type":"enabled"}`、`reasoning_effort`；`response_format: {"type":"json_object"}` 需同时在 prompt 中要求 JSON |
| 不支持/忽略 | `frequency_penalty`、`presence_penalty` 被忽略 |
| 错误处理 | HTTP 429 需指数退避；HTTP 402 表示余额不足，应给出明确提示 |
| 并发上限 | flash 2500 / pro 500（账户级，个人使用远超需求） |
| 参考价格（非峰时） | flash：输入 $0.15 / 输出 $0.60 每百万 token；pro：输入 $0.66 / 输出 $1.98 |

**对你方案的直接影响**：

1. 你写的 `deepseek-flash` **是当前有效且最省钱的模型名**，无需改动。
2. **但模型名在快速迭代**（一年内从 `deepseek-chat` → `deepseek-v4-flash` → `deepseek-flash`）。因此「设置中可选模型」**不能硬编码枚举**，必须做成「预设下拉 + 自定义模型 ID 输入框」，否则每次官方改名都要改代码发版。这正好把你原本的需求变成了一个必要的架构决策。
3. 参数需按模型能力白名单校验：`thinking`/`reasoning_effort` 并非所有模型都支持，界面应做启停与提示。
4. **成本估算**：按每天 2 道题、每道 2k 输入 + 1.5k 输出 token 计，用 flash 约 $0.0012/天，全年不到几元人民币（峰时价格翻倍，仍可忽略）。可放心使用，但要记录 token 用量便于观察。
5. **质量与合规风险**：AI 可能给出错误解法；所有 AI 输出标注「AI 生成，仅供参考」，且**不自动写入正式题解**，需人工确认。题面/代码会发送至第三方 API，虽为个人学习用途，仍应在设置页明示。

### F7 自动导出文档

- 模板化聚合：日期范围内的「新题 + 复习题 + 完成状态 + 思路总结 + 代码片段 + AI 分析摘要」→ 单份 Markdown 复盘文档。
- Markdown 原生生成，零外部依赖、可直接纳入 git、便于二次编辑。PDF/DOCX 可后续通过 Pandoc / Typst / python-docx 扩展，但会引入额外二进制依赖，不宜放进 MVP。
- **可行性**：🟢 高。

### F8 本地架构与运行环境

- 本机已具备：Node v22.22.2、npm 10.9.7、Python 3.13.14、pip 26.1.2、Java 21、Git 2.55，且 git 全局 `user.name` / `user.email` 已配置。无需额外安装运行时。
- 单机单用户、`SQLite` 单文件、仅监听 `127.0.0.1`、无账号体系、无云依赖 → 零运维、启动快、数据完全在自己手里。
- 需联网的仅两处：题库同步、DeepSeek API；断网时核心闭环照常可用（对应 D-15）。

## 8. 版本管理与回退策略（本轮已落地）

针对你「避免某一版出错无法回退」的要求，约定如下，并已在本轮完成基础设施：

1. **仓库基线**：已 `git init`，首个提交仅包含文档与仓库配置，作为 `v0.1.0-docs` 基线。
2. **忽略清单**（`.gitignore`）：`.env*`、数据库文件（`*.db`/`*.sqlite3`）、导出产物、`node_modules`、`__pycache__`/`venv`、编辑器缓存，以及**含有明文密钥的原始方案 txt**。
3. **分支**：`main` 只放可运行稳定版；日常开发在 `dev`，合并前确保可启动。
4. **里程碑标签**：每完成一个里程碑打 tag（`v0.2.0-m1`、`v0.3.0-m2` …），随时可 `git checkout <tag>` 回到任一可运行版本。
5. **提交规范**：Conventional Commits（`feat:` / `fix:` / `docs:` / `refactor:` / `chore:`），一个提交只做一件事，便于定位与 `git revert`。
6. **数据库变更**：一律走 Alembic 迁移脚本，禁止手改表；回退代码时同步执行 `alembic downgrade`，保证代码与 schema 版本一致。
7. **数据不在 git 里**：SQLite 与导出文件不入库，另配每日自动备份 + 手动 JSON 快照，避免「代码回退了但数据没了」或反向问题。
8. **回退手册**：`git tag` 查版本 → `git checkout <tag>` 验证 → 需要保留历史时用 `git revert <commit>`（避免对已提交历史使用 `reset --hard`）。

> 注意：原始方案 `刷题助手第一次规划.txt` 因含明文密钥被 `.gitignore` 排除，不会进入任何提交。其**脱敏后的完整内容**已归档于 `docs/02-项目开发需求文档.md` 附录 A，因此需求原文仍有版本记录。

## 9. 补充分析：两种题目获取方案（2026-11-07 追加，结论待确认）

来源：`题目爬虫方案修正.txt`

> - 方案 1：我打开浏览器，你自己输入地址，搜索页面上的题目进行总结
> - 方案 2：直接通过爬虫去搜索题目

### 9.1 先厘清一个关键判断

**用浏览器还是用 HTTP 客户端，并不改变自动化访问的性质。** 合规边界由三件事决定：

1. 是否自动化批量访问被 `robots.txt` / 服务条款禁止的路径（LeetCode 明确禁止 `/api/`、`/graphql`）；
2. 是否绕过反爬机制，或复用登录 Cookie 做无人值守采集；
3. 是否把第三方题面、样例、官方题解原文批量存储或再分发。

因此，让程序自动翻页、批量抓 LeetCode / 洛谷页面，即使跑在真实浏览器里、带着登录态，**仍然是方案 2 的风险**，还会额外触发 Cloudflare。

但方案 1 如果保持「**人打开页面 → AI 只处理当前这一页 → 产出摘要**」，性质完全不同：那是辅助阅读，等同浏览器插件，风险极低；而且天然绕开了站点改版问题——AI 当场理解页面，不依赖固定 CSS 选择器，不用为每次改版重写解析规则。

### 9.2 方案 1 的两种载体（重要区分）

| 载体 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| A 项目功能 | 浏览器扩展 / 书签脚本，点一下把当前页正文 POST 到本地服务，调 DeepSeek 总结后写入题库 | 常驻可用，可脱离对话使用 | 需额外写扩展与本地接口，仍要处理页面正文抽取 |
| **B 会话式工作流（推荐）** | 不把采集写进项目；每次需要补题时，由 AI 助手用浏览器能力打开站点、搜一批题、总结成结构化 JSON/CSV，再走既有导入接口写入题库 | **项目内零爬虫代码**、零反爬维护、站点改版不影响项目、每次导入内容可见可审 | 需要用户发起一次对话，不是软件后台自动跑 |

原话中「**我打开浏览器**」意味着人在场、有真实会话，正好对应载体 B 的「人在回路」。这实际上是把「自动搜索题目」从**软件功能**改写为**由助手执行的工作流**：项目复杂度显著下降，而你要的结果（结构化题库）不变。

> 这也是本轮分析最重要的收获：方案 1 不必做成一个模块，它可以是一条工作方式。

### 9.3 方案 2 的有效边界

方案 2 不该整体否定，但必须**限定为官方公开 API**：

- ✅ Codeforces `problemset.problems`、AtCoder Problems 公开 JSON：结构化、免登录、稳定，本来就是「爬虫」最规范的形态，且比爬 HTML 稳得多。
- ❌ 抓 LeetCode / 洛谷 HTML 页面：`robots.txt` 禁止或灰色、Cloudflare / 登录态、页面改版即失效、题面版权。

换句话说，**方案 2 的合规子集就是本报告 F1 已经建议的 L1 层**——两者不是竞争关系，而是同一件事的两种说法。

### 9.4 推荐：三层组合，而不是二选一

| 层 | 做什么 | 触发方式 | 覆盖站点 | 合规 |
| --- | --- | --- | --- | --- |
| **L1 官方 API 目录同步** | 批量拉元信息：题号、标题、标签、难度、原题链接 | 项目内手动或定时 | Codeforces、AtCoder | 🟢 |
| **L2 浏览器内单题总结** | AI 读当前页，产出知识点、难度建议、摘要、笔记草稿 → 结构化文件 → 导入 | 用户主动发起，单页 / 按需 | 洛谷、力扣、蓝桥杯及任意站点 | 🟢 |
| **L3 手工录入** | 题号 + 外链、CSV 批量导入 | 界面 | 兜底 | 🟢 |

**L2 顺带补上了原设计的一个缺口**：D-12 原本要求 AI 分析的题面由用户手动粘贴，现在可由浏览器当前页直接送入，且仍不批量落库原文。

### 9.5 明确的禁止项（已同步写入需求文档 FR-04 / NFR-05）

- 自动批量翻页、自动遍历题目列表页；
- 绕过 Cloudflare / 验证码，或复用登录 Cookie 做无人值守采集；
- 调用 LeetCode 被 `robots.txt` 禁止的 `/api/`、`/graphql` 端点；
- 批量存储或导出第三方题面、样例、官方题解原文。

2. **D-19**：是否允许本地保存单题题面快照（默认否，只存 AI 摘要与笔记）？
3. **D-20**：是否同意方案 2 限定为官方 API、放弃 HTML 页面爬取？
